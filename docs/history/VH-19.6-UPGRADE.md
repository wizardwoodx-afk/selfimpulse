# VH-19.6-UPGRADE.md — the Federation release

**Vouch Harbor 19.6.6 "Federation"** — the console release: the federation
plane moves onto the live path, built on the frozen **19.5.6 "Reach"** core.

## 19.6.6 — the console, and federation on the live path

The 19.6.4 reviewer was right: standing authority, the common ledger and
regulated activation were verified subsystems that the production bridge
never called. 19.6.6 wires them into the crossing the console actually runs,
and rebuilds the app surface around it:

1. **One console, and it IS the app.** The multi-dock shell is deleted. The
   Generalist's dark operations console is the whole product — crew rail,
   run stream, handoff ledger, federation plane. The Generalist keeps ONE
   deterministic face derived from the name its owner gives it; every
   specialist carries a deterministic mark (probe/face, 10 checks).
2. **Standing authority on the live crossing** (`src/vh19/federation/live.ts`).
   The console issues a grant both owners sign once; each crossing under it
   keeps its own envelope and nonces and mints one acknowledgement per side,
   bound to that envelope digest. Out-of-scope, spent, lapsed and revoked
   grants escalate to a per-crossing human decision — escalation is designed
   behaviour, never an error. A grant never overrides earned pair standing;
   it adds one co-signed trust unit to the mesh's own ladder.
3. **The common ledger rides every outcome.** Crossed AND refused rows land
   in both stores with both receipts; the roots over each store are compared
   on the receipt itself; the shared screen is a derived view.
4. **Regulated activation on the routing path.** The registered regulated
   bench stays unrouted until a signed, complete, current activation exists;
   the refusal names every gap — a name is not an authorisation.

New probes: probe/face (10), probe/fedWired (18). Gates: tsc 0 · 137 probe
suites green · offline 136/136.

If you are upgrading from 19.6.4: nothing in the frozen core moved; the
federation modules keep their byte-stable seams. What changed is what the
console calls.

## What this release is

19.5.6 taught the harbor to *reach* — a real computer-use plane, an Authority
layer signing mandates, VouchMesh co-signing joint receipts in the live
handoff path, a crew of 1,150 specialists. What it did not yet have was the
thing this product is *for*: **one owner's agents working directly with
another owner's agents, with a human on both sides and evidence either side
can verify offline.**

19.6 is that layer. It is deliberately small, and it is built out of parts the
engine already ships:

## The three review findings, closed

### 1. The responder's approval is now a real approval

**Finding.** The alpha's `respondToCrossing()` inferred permission from history:
it called `hasCrossedBefore(pair)`, and a prior `success` ledger row made that
true. A ledger row is a *record*; an approval is a *decision*.

**Fix.** Both sides now present the same object: a `FederationApproval` —
ECDSA P-256, by a named human, over a body bound to
`{ pair, side, capability, envelopeDigest, nonce }`, with an expiry, spendable
exactly once.

**Proof.** `probe/fedCrossing.test.ts` §2 inserts exactly the historical row
the alpha trusted, presents no responder approval, and requires the crossing to
be refused as `responder-human-first` with the words *"a previous successful
crossing is a record, not a decision."* §4 hands the responder the *initiator's*
valid approval for the same envelope and requires `wrong-side`.

### 2. Distributed evidence, local trust — said in those words

**Finding.** Each harbor keeps its own trust ledger, so their trust scores can
diverge. The reviewer asked for the distinction to be stated plainly.

**Fix.** It is now stated in the module doc, the API and the docs:
**distributed evidence, local trust state.** Envelopes, approvals and receipts
are portable and verifiable by either party offline. The trust *score* is local
observation on each machine and may legitimately differ. There is deliberately
no central reputation server — `federation/bridge.ts` **reads** standing from
VouchMesh and never writes it; pair trust moves only through VouchMesh's own
`recordJointOutcome`. `probe/fedCrossing.test.ts` §6 pins that the default
standard reader is the live mesh ledger, which knows a fresh pair not at all.

### 3. One identity system, not two

**Finding.** `createHarborKeys()` kept a private key in a closure and never
persisted it — fine for a module, useless as an identity.

**Fix.** `federationIdentity()` is a thin resolver over the harbor's existing
authority identity: the same owner keypair that signs mandates, resolved through
`ownerKeyStore` (native keystore → AES-256-GCM → session, honestly flagged).
The federation layer **mints nothing**. The anchor it issues carries a
*proof of possession* — a self-signature over the anchor body — because a
claimed public key proves nothing about who holds the private half.
`probe/fedIdentity.test.ts` pins that the federation identity's public key is
byte-identical to the authority identity's, that a session-scoped anchor is
refused when durability is required, and that re-pointing the fingerprint
breaks verification.

## 19.6.4 — approve once, then autonomous; one place to check; activation bound to a key

Four things: the reviewer's two conditions, and two product asks taken as
architecture rather than shortcuts.

**1. The hygiene find — fixed, and pinned so it cannot come back.**

`verify/BUILD-INFO.txt` is the provenance file a reader opens to identify the
artifact, and it still called the federation bench *"the 1,560 census"* and
stated the fleet as `1,560 = 1,150 + 410` while the build ships **1,790 = 1,150
established + 640 registered**. `versionDrift` did not catch it because it pins
versions, counts and doc titles — not the fleet sentence. The fix is two-part:
the text is corrected (the 19.6.0 value stays, dated, as history), and
**`probe/fedFleet` §2b now fails the gate when the provenance file's `fleet:`
line disagrees with the code.** A record that drifts is a bug; a record that
*cannot* drift is a control.

**2. Activation is owner-key bound — the reviewer's second condition.**

`enabledBy` was a free-text name: enough to say "priya enabled this bench", not
enough to say "the owner identity behind key X enabled this". Contained while the
bench is unrouted and the module holds no capability — not contained the moment
anything is wired to it. `federation/regulatedPolicy.ts` now signs activation
with the harbor's owner authority key, bound to exactly what the reviewer listed
— **enabledBy · owner key · activation digest · jurisdiction · context · renewBy**
— plus the domain list, because a signature that did not cover the domains could
be re-aimed at another bench.

```ts
const signed = await issueRegulatedActivation({ domains, enabledBy, jurisdiction, context, renewBy }, ownerKeys, now);
await verifyRegulatedActivation({ ...body }, ownerKeyPem, now);
//   → { ok: false, reason: "unsigned-activation",
//       detail: "this activation names a person but carries no owner-key signature
//                — a name is not an authorisation" }
```

Completeness is judged **first** (signing never launders an incomplete
activation), a foreign key does not verify it, a tampered jurisdiction or a
swapped domain list breaks the signature, and the filed record carries the same
two sentences as an approval:

```
attests     the harbor owner's authority key enabled this regulated bench, naming the human
            who authorised it, in the jurisdiction and context recorded here, until the renewal date
notAttested that this jurisdiction or any authority in it has accepted, licensed or approved this use
```

**3. Product: approve once, then autonomous — without losing the evidence.**

The crossing plane asks a human on each side, every crossing. That is right for
the first crossing and wrong for the tenth of the same kind in the same day. Both
owners now approve **once**, and the pair works on its own under that grant
(`federation/standing.ts`).

The distinction this module is built around: **the human leaves the loop; the
evidence does not.** Every crossing still carries its own envelope, its own
nonces and its own receipt, and each is authorised individually by an
acknowledgement bound to *that* envelope digest and *that* side's nonce. What the
grant supplies is authority, not permission to skip the record.

Autonomy is bounded, and the bounds are the feature:

| Bound | Refusal when it binds |
|---|---|
| enumerated capabilities (never `*`) | out-of-scope → **`escalate`**: returns to a per-crossing human decision |
| total budget (`maxCrossings`) | `grant-exhausted` — "set a new grant, which means two humans looking again" |
| rate window (`windowMs`/`windowMax`) | `window-exceeded` — wait for the window, don't raise the bound |
| expiry (`expiresAt`) | `grant-expired` |
| revocation, by either side, with a reason | `revoked` — naming who and why |

Both owners' keys sign the identical canonical body, so neither side can create
authority over the pair alone; a wildcard capability, an unbounded budget or a
grant naming only one human is refused at issue time. And the acknowledgement
prints the sentence that keeps autonomy honest:

```
attests     the harbor owner's authority key authorised this crossing IN ADVANCE, under a
            standing grant that names the human who set its scope and its bounds
notAttested that a human reviewed this specific crossing — the grant was approved once, and
            its bounds are what stand in for a per-crossing decision
```

**4. Product: one common place to check — as a view, not a shared store.**

Both users should be able to look at the same thing. A shared server would be a
shared **trust anchor**: whoever holds it can drop a row or show each side a
different history, and both parties would have to trust the holder — which,
between two companies, is the thing this plane exists to avoid. So
(`federation/ledger.ts`):

- both sides record the **same joint row** for a crossing, into their **own** store;
- each side derives a **root** over its own entries independently and the roots are
  compared — **derived, never carried**, exactly as an envelope digest is recomputed;
- equal roots produce a co-signed record whose own text says what that means and
  what it does not: *"agreement about what happened is not agreement about what
  should have happened."*
- divergence is named **in words down to the crossing id**, and a **missing** row
  and a **changed** row are different findings with different sentences;
- `pairLedgerView` is the shared screen: the union in time order, a row only one
  side holds *marked* (`initiator-only` / `responder-only`), a row the two hold
  differently *flagged and handed over unmerged* — merging is how a disagreement
  gets lost;
- an auditor may hold the agreed root. That mirror can prove a later divergence;
  it can never assert what is true, because it holds one number, not the records.

## 19.6.3 — the full gate, reproducible inside a short window

**The requirement, in the reviewer's words:** the full 134/134 offline
reproduction on a dependency-free environment, before anything is called final.
That was the last thing standing between this line and a freeze, and it was
fair — the gate took ~86s on a two-core box and a reviewer's window was shorter,
so a release claim went unreproduced.

**Met, and measured.** The archive extracted alone — no `node_modules`, plain
`node` — runs the whole pack in a single window:

```
$ node verify/run.mjs
OFFLINE VERIFY SUMMARY: 134 passed, 0 failed. (node v20.20.2)
real 1m20.535s        # two cores
```

Meeting it meant fixing three real leaks, because "dependency-free" was checked
by extracting the archive rather than by reading the claim. (1) The MCP engine
`tools/mcp-engine.mjs` imported `zod` — the host could not start without an
install, and five suites that spawn it timed out; it now **bundles its runtime
dependencies** and starts from a directory containing nothing else, with the
bundled copy disclosed in `NOTICE`. (2) `tools/drill-benchmark.mjs` and
`tools/external-model-validation.mjs` refused without esbuild, so `drill`
self-skipped; the pack now compiles both entries into `verify/specs/` and the
tools fall back to them, saying which path they took. (3) `mcpSdkClient` E4 read
the installed SDK's version; it now verifies the **declared** pin everywhere and
the **resolved** version only where an install exists — stated, not skipped.

**1. The gate can now be run in pieces, and the pieces are honest about being
pieces.**

```bash
node verify/run.mjs                    # the whole gate, unchanged (~86s on 2 cores)
node verify/run.mjs --shard 1/4        # quarter 1 of 4 — a deterministic slice
node verify/run.mjs --time-budget 30   # run until 30s are nearly spent
node verify/collect.mjs                # merge every shard into the whole verdict
```

- A shard is a slice of the **sorted** suite list, so two machines with the same
  tree shard identically — a merged verdict is a verdict about the tree, not the
  machine.
- `--time-budget` never kills a suite mid-flight: the budget decides what is
  *started*, never what is *judged*.
- A budgeted run that stops early **exits 3, never 0**, and names every suite it
  did not reach. A partial run that exits 0 is the exact failure this runner
  exists to prevent.
- `collect` merges the records and returns **0 only when the union covers every
  bundle**. One shard of four merges to `34 passed, 0 failed, 100 not covered` →
  exit 3. All four merge to **134 passed, 0 failed, 0 not covered** → exit 0.
- Verified here, in the extracted archive with no dependencies: four shards
  (34 + 34 + 33 + 33), each inside a 60-second budget, merged to
  **134 passed, 0 failed, 0 not covered**; drop one shard and the merge says
  **101 passed, 33 not covered** and exits 3. The full record is in
  RELEASE-VERIFICATION.

**3. The batch generators now run with no `node_modules` at all.**

The reviewer could not run them because compiling a `.ts` spec needs esbuild. The
*drift check* was already available offline — the batch probes build each bench
from its spec and compare it to the shipped snapshot inside their bundles — but
the command a maintainer reaches for was not. `tools/build-offline-verify.mjs`
now also writes the compiled specs to `verify/specs/` (sha256 in
`verify/MANIFEST.json`), and `tools/generate-batch.mjs` falls back to them,
announcing which path it took:

```
reach: spec loaded from pre-compiled verify/specs/reach.spec.mjs (sha256 matches MANIFEST)
reach batch: OK — 200 entries over 40 domains, snapshot matches the spec
```

The esbuild import is lazy on purpose: a static import makes the whole tool fail
to load when the dependency is absent, which is exactly the case being fixed.

**4. "A catalog entry is not regulatory authority" — now a rule in code.**

The reviewer's product note, taken as a design constraint rather than a comment.
`src/vh19/federation/regulatedPolicy.ts` holds it: a regulated bench is never
enabled by default, by upgrade or by a caller, and activation is not a boolean —
it names a jurisdiction and a context, by a person, with a date it must be
reconsidered.

```ts
judgeActivation({ domains, enabledBy, jurisdiction, context, renewBy }, now)
  → ok:true  { attests: "priya enabled 2 regulated domain(s) as advisory under IN, until …"
               notAttested: "that this jurisdiction or any authority in it has accepted,
                             licensed or approved this use" }
  → ok:false "no-jurisdiction"  "the governing rule must be named; an implied jurisdiction
                                 is a refusal, because the law is not universal"
```

Every way of leaving an activation vague is refused by name (`no-owner`,
`no-domains`, `no-jurisdiction`, `weak-jurisdiction`, `no-context`, `no-renewal`,
`expired`), `activationGaps()` returns the checklist a UI renders, and
`REGULATED_DISCLAIMER` is the sentence every regulated-capable surface prints.
The module holds no capability and routes nothing — it exists so the product
cannot quietly acquire authority it was never given.

## 19.6.2 — the signature, stated precisely; 230 more specialists; a faster verification path

Three things came back from the read of 19.6.1. Two are corrections to how this
release *describes itself*, and the reviewer was right about both.

### 1. These are OWNER-KEY approvals, and the release now says so

**The finding.** The code and docs said "both humans" approved a crossing. What
the cryptography actually shows is that **each harbor's owner authority key**
approved — the same key that signs mandates — *naming* the human it acted on
behalf of. A `human` field is a claim by the key holder, not a separate human
credential. Nothing was wrong with the mechanism; the words were stronger than
the mechanism.

**What is proven:** *the owner-controlled authority key approved this crossing,
and it named who authorised it* — bound to pair, side, capability, envelope
digest and nonce, spendable once.

**What is not proven:** *that the named human authenticated with a credential
distinct from the owner key.* No second factor, no human-held key, no device
attestation stands behind the name.

**Made structural, not just editorial** — because the failure mode is a UI
sentence that quietly upgrades the claim:

| Where | What it now carries |
|---|---|
| `APPROVAL_SIGNER` | `"owner-authority-key"` — one word for who signed |
| `APPROVAL_ATTESTATION` | the sentence above, printable verbatim on a receipt |
| `APPROVAL_NOT_ATTESTED` | its explicit limit, travelling beside it |
| `approvalRecord()` | `signedBy`, `attests`, `notAttested` and **`ownerKeyHandle`** — which key signed, and which human it named, side by side |
| `CrossingOutcome.attestation` | both sentences at the top level of the in**digest** |

`probe/fedApproval` §"WHAT THE SIGNATURE PROVES" pins it semantically, not just
verbally: **one owner key approves twice naming two different humans**, both
verify, and the filed records keep the two humans apart with the same key handle
— which is exactly what "on behalf of" means and what a separate credential would
not allow. A second key naming the *same* human is a different approver, and the
records' digests differ.

## 19.6.1 — the two refinements from review

Both came back from the first external read of 19.6.0, and both were right.

### 1. Two local trust stores, not one reader for both sides

**The finding.** `crossFederation()` took a single `standing` reader and used it
for the initiator's grant AND the responder's grant. The docs said *distributed
evidence, local trust state* — and said the two machines' scores may legitimately
differ — but the runtime API could not represent that difference at all. The
probe passed only because it injected one `"proven"` reader for both.

**The fix.** Standing is now read PER SIDE:

```ts
crossFederation(parties, {
  standingInitiator,   // the initiator harbor's own local store
  standingResponder,   // the responder harbor's own local store
  stores: { initiator: "reykjavik", responder: "lisbon" },
  ledger, now,
})
```

The initiator's grant is computed against the initiator's store and the
responder's against the responder's — and the **outcome records which store each
tier came from**, inside the digest:

```ts
standingSource: { initiator: "reykjavik", responder: "lisbon", shared: false }
```

`shared: true` only when both sides genuinely read one store — the
single-machine case, where a caller passes the legacy `standing` reader or the
same function twice. The receipt then says so rather than implying two
independent observations agreed. When the two stores *disagree*, the refusal
names the store that said no, and says why that is legitimate:

> the responder's own local trust store (lisbon) lends this pair nothing: …
> — read from the responder's store (lisbon), not the other side's (chennai);
> local trust state is per machine and the two are free to disagree

`probe/fedCrossing` §9 proves it three ways: two readers each consulted about
this pair and the outcome marked `shared: false`; the responder's store refusing
while the initiator's vouches (and the mirror image, same envelope, opposite
outcome — impossible with one reader); and a single-reader caller correctly
reported as one store.

### 2. The Face is KEY-derived — decided, implemented, documented

**The finding.** 19.6.0 seeded the mark from `harbor:<owner>`, so the same owner
with a rotated key kept the same face — while the docs called the mark "derived
from the identity". Both readings were defensible; they disagreed, which was the
defect.

**The decision.**

```
the mark a counterparty pins is derived from the CANONICAL PUBLIC KEY
```

Rotation produces a **new** mark; a swapped key cannot keep the old one.
`faceSeedForKey()` hashes the canonical key material (the Base64 body of the
SPKI PEM — so a PEM and a JWK of the same key derive the SAME mark, however
either was line-wrapped), and `verifyAnchor` re-derives the handle **from the
PEM inside the anchor**, so a mismatch is caught twice: by the derivation and by
the self-signature that covers the handle.

Two kinds of mark now exist in the product, and they are **labelled, not
confused**:

| Kind | Seed | Used for | On screen |
|---|---|---|---|
| **key-derived** | `faceSeedForKey(publicKeyPem)` | a harbor identity — its identity of record IS its key | `KeyFace` — peers in the collaboration desk |
| **subject-derived** | `sigilOf("<kind>:<id>")` | a run-derived subject with no key of its own | `SigilFace` — mission-crew cards |

The hover text for each says which one it is, and neither claims to be proof:
*the key is the proof; this is how you recognise it.*

The probe caught a real bug on the way: `keyHandle()` was hashing the raw PEM
with a second derivation rule, so the face's own reported handle disagreed with
the standalone key handle — and disagreed again when the same PEM was
re-wrapped. There is now one rule (the handle of a mark is the handle of its
seed) and `probe/fedIdentity` §3 pins the re-wrap invariance.

## The Face: derived, not selectable

The genre's default is an avatar you can shop for — a gallery, a colour picker,
a "new set" button. That is a costume, and a costume is an impersonation
surface: a face two people can wear carries no weight, and a face you can
re-roll cannot be evidence of anything.

The 19.6 sigil is a **heraldic device derived from the identity itself**:

```
identity ─► SHA-256 (pureSha256) ─► field · division · semé · chief · charge
                                  · tincture · ground · bordure · tilt
                                  ─► 4×4 fingerprint handle
```

* **No picker.** There is no gallery and no re-roll. The only way to change a
  face is to change the identity it comes from, which is a real act.
* **No eyes, no mouth.** Charges are drawn singly, as a column, or in bend —
  the code has no path that places two charges on the same row, because the
  first draft did and rendered as a tiny smiley. `probe/fedSigil.test.ts` §4
  pins it.
* **The palette is VH's.** Every tincture is an existing token (the avatar inks
  plus the atelier accents); the probe asserts membership, so no new hue can
  creep in.
* **Distinctness is measured, not asserted.** 23 discrete bits; the probe
  reports the closest pair and the TRUE exact-collision count in a sample
  rather than an average. The honest statement, repeated in the docs: a sigil
  is a recognition aid with a 16-hex handle beside it — **the key is the
  proof.**
* **Seven states, and two of them are not the same fact.** idle · thinking · acting · gate (awaiting a
  human) · sealed (verified) · refused (the harbor decided) · failed (the run
  broke). Refused carries a slash through the field; failed carries a cross
  above it. The list lives in the module (`SIGIL_STATES`) and the sheet, the
  montage and the app all read it, so no surface can invent a state.
* **On screen.** `federation/SigilFace.tsx` puts the Face where identities are:
  each mission-crew card in the VH-19 door wears its member's derived mark in
  the state that member's run ended in, and each **bound peer identity** in the
  collaboration desk wears the mark its own anchor attests to — same
  derivation, so the face beside a name is the face that name proved.
* **Both languages coexist.** 19.5.0's gem avatars (`avatarEngine.ts`,
  `avatar.tsx`) are untouched and still mark the Generalist's own presence — a
  portrait for an agent at work, a device for an identity being pinned. The
  sigil is the second language, used where the subject is an identity rather
  than a working presence.

Design iteration is recorded: the first sheet rendered, was looked at, and

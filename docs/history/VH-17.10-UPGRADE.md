# Vouch Harbor 17.10 "Warrant"

**Protocol 0.10.4 · released 12 September 2026 · current point release 17.10.1**

A security release. One defect was found and closed, one integrity defect was
closed, and the protocol gained a rule it should always have had.

---

## Read this first if you run a harbor

**17.10 changes what a grant is allowed to say.** If you issue authorizations on
a harbor, read [§1](#1--scope-bounded-delegation-the-security-fix) before you
upgrade. There is a one-line escape hatch if you need time to migrate.

## What was wrong

### 1 · Scope-bounded delegation (THE SECURITY FIX)

**Any identity on a harbor could mint authority for any action — including
actions it had no capability to perform.**

`verifyGrantAuthority()` has, since 17.6.1, answered *"may this identity
delegate?"* It checked that the granter was **attested** — holding a capability
declaration or a received endorsement. It never asked *"may this identity
delegate **this**?"*

That gap meant attestation was being read as authority. A capability
declaration is a **self-signed claim**. It is not a grant from anyone. Treating
it as a licence to delegate anything handed every participant unbounded
authority-minting power.

Reproduced before the fix — an identity declaring only `read:public`:

```
attacker.authorize(victim, "write:purchase_orders")  →  ACCEPTED   (ledger seq 17)
victim commits under that authority                  →  ACCEPTED   (ledger seq 18)
attacker.authorize(victim, "*")                      →  ACCEPTED   (ledger seq 19)
```

Nothing was forged. Every signature was valid. No keys were compromised. The
attacker acted alone. This is **privilege amplification**, and it is the same
class of failure the WeClawArena benchmark's largest attack family probes —
*"outside the owner's mandate."*

**After 17.10**, both legs are refused:

```
attacker.authorize(victim, "write:purchase_orders")  →  policy:grantor-out-of-scope
attacker.authorize(victim, "*")                      →  policy:wildcard-grant-requires-wildcard-authority
```

### 2 · Assurance was a payroll count

`harborRerate()` returned `60 + seats * 3`. **Assurance rose every time you
added an agent**, regardless of whether any work was ever verified. Its
docstring claimed to walk "sealed receipts + learned skills"; both were
hardcoded to `0`. It bypassed `scoreAssurance()` — an honest module that
refuses to produce a number without measured evidence.

An assurance figure that measures headcount is worse than no figure. It reads
as evidence and is not.

`harborRerate()` now delegates to the real scorer. Evidence is gathered from
the mission loop's own ledger — sealed receipts, cross-vendor verification,
arena verdicts, budget adherence, human ratings. **With no measured runs the
score is `unevaluated` and the number is `null`.** Nothing simulated counts.

This is a **breaking change to the return shape**: `assurance` is now
`number | null`, and the report carries `status`, `band`, `factors`, `measured`
and `note`.

## 1 · Scope-bounded delegation (the security fix)

### RULE 3 — a granter may only hand out authority it holds

Before issuing an authorization, the harbor now requires the granter to hold,
in its own right:

| | Held as | Example |
|---|---|---|
| **a** | the exact action, or `*` | `write:purchase_orders` |
| **b** | a delegation token for the grant's scope | `delegate:procurement`, `admin:billing` |
| **c** | for a `*` grant: a `*`-class token | `*`, `delegate:*`, `admin:*` |

Held means a **capability declaration naming it** or a **live grant naming it as
subject** — revocation- and expiry-aware. Anything else is refused with
`policy:grantor-out-of-scope`. **Deny by default.**

A wildcard grant requires wildcard-class authority: a narrow capability can
never be widened into unbounded authority.

**Sub-delegation may narrow, never widen.** A delegated grant is accepted only
when the parent grant covers what is being passed on.

### The three rules together

| Rule | Question | Since |
|---|---|---|
| 1 · Attested granter | *may* you delegate? | 17.6.1 |
| 2 · Capped delegation chain | how deep? | 17.6.1 |
| **3 · Coverage** | **what may you delegate?** | **17.10** |

Endorsement supplies **standing**. Capability supplies **scope**. Both are now
required.

### Defence in depth

`findAuthorization()` — the consumption side — now re-checks issuer coverage at
lookup time. A grant whose issuer has since been narrowed or revoked stops
working even if it was issued under the old rule. This closes the upgrade
window for pre-existing ledgers.

Refusals are counted separately in `metrics.grantAuthorityRejected` and audited
with the action, scope and the tokens the granter actually held.

### Migrating

Legitimate flows need one change: **declare what you delegate.** An approver who
grants `write:purchase_orders` must hold `write:purchase_orders` or a
`delegate:<scope>` token.

```js
// before — declared an unrelated capability, then granted anything
await alice.declareCapability(["delegate_portfolio_ops"]);
await alice.authorize(bob, "execute_trade", { scope: "portfolio-v3" });

// after — declare authority you actually hold
await alice.declareCapability(["delegate:portfolio-v3", "read_market_data"]);
await alice.authorize(bob, "execute_trade", { scope: "portfolio-v3" });
```

**Escape hatch.** Set `VH_GRANT_POLICY=compat` to restore 17.6.1 attested-only
semantics and keep existing flows running. It **reopens the vulnerability** —
use it to migrate, not to stay. `VH_GRANT_POLICY=off` disables the gate
entirely and exists for test fixtures only.

## 4 · Why the codename

A *warrant* is an authorization that names **who** may act, **on what**, and
**within what bounds**. That is the whole of this release: the harbor already
knew who was trusted; it now knows what they were trusted with.

## 5 · What 17.10.1 adds (external review of 17.10.0)

A review of 17.10.0 found that this document's headline claim was **only half
true**, and it was right.

`harborRerate()` was fixed. A **second** fabricated assurance formula survived in
`src/app/harbor.tsx`:

```ts

```

…and it was rendered on two live surfaces — **Harbor → "Safe harbor"** and

from one path and an invented one from another, to the same user.

**Fixed:** `assuranceScore: number` is gone. `HarborTotals.assurance` is the

Reintroducing the 17.10.0 defect makes it fail on three independent shapes.

The generalisable lesson, which is the reviewer's: *a "security fixed" release
must not pass on the strength of the new module's tests alone. When you fix a
concept, search the whole live runtime for every other implementation of that
concept.* That search is a grep, and a grep belongs in the gate.

Also corrected here: this document previously claimed stale installers sit in
`verify/`. They do not — the tree ships no installer binaries at all.

## 7 · 17.10.3 — the adversarial campaign, and what it broke

The reviewer's closing recommendation was: *stop adding security subsystems and
try to break Warrant.* This release does that, with a harness that ships —
`protocol/wcarena/adversarial-campaign.mjs`, eleven attack classes against a
live harbour plus a legitimate control.

**It broke.** RULE 3 enforced *a granter may only hand out what it HOLDS*, but
"holding" was still established by a **self-signed capability declaration**. Any
participant could join, declare `["*"]` for itself, and mint unbounded authority
to an accomplice — two messages, no forgery, no key compromise, no collusion.
The harbour's own ledger recorded it: the stranger's `authorization` **accepted**
(seq 9), the accomplice's `agent_action` **committed** (seq 10). The release that
closed "attestation read as authority" had left the same amplification standing
one level up.

**PROTOCOL v0.10.5 — RULE 4: unbounded authority is never a self-claim.** A
`*`-class token (`*`, `delegate:*`, `admin:*`) counts only when the harbour
**designated** its holder: the root key automatically, plus operator-named
fingerprints (`VH_WILDCARD_AUTHORITIES`). Everything else is refused as
`policy:wildcard-authority-not-designated`, with the claim itself recorded in the
audit line's `held` array so an operator can see who tried. Unbounded authority is
**never transitive**, the parent-`*` shortcut on the delegated path is gated the
same way, and both issuance and consumption enforce it (the coverage re-check
threads the designation list, as do `assessActionRisk` and `authorization:find`).
Named capabilities are unaffected — the ordinary "I hold `write:offers`" path is
byte-for-byte the behaviour it always was.

**After the fix, the same campaign: 11/11 refused, control intact.**

| Attack class | Result |
|---|---|
| self-declared `*` ⇒ mint `*` | **REFUSED** (was **committed** — seq 9/10) |
| self-declared `delegate:*` ⇒ confer payroll | **REFUSED** (was committed) |
| revocation race (grant outlives its issuer's capability) | refused at consumption |
| expired authority | refused |
| action-name smuggling (`write:offers_v2`, `WRITE:OFFERS`, whitespace) | refused |
| scope smuggling (`procurement-evil`, `procurement:evil`) | refused |
| action substitution under a real grant | refused |
| **CONTROL · legitimate grant → commit** | **PERMITTED** |

`protocol/test/selftest.js` **140/140** (was 134): six new checks, including the
unit-level proof that **designation makes the same claim usable** — the rule is
not "wildcards never work", it is "wildcards are never self-evident".

**Residual risk, stated rather than papered over.** A self-signed capability
declaration still establishes *scope* for named actions (Decision 1's bootstrap:
reputation-weighted, revocable, audited). RULE 4 removes the *unbounded* case. It
does not turn a claim into proof, and this document does not claim an
attested-claim-free harbour.

## 9 · 17.10.5 — RULE 6, the two bounds the campaign measured

The attacker-grade campaign shipped in 17.10.4 (`wcarena/warrant-compromise-campaign.mjs`)
did not only attack — it *measured*, and reported two residual weaknesses instead
of hiding them. The review kept 17.10.4 as the Warrant trunk and declined to
freeze Warrant until they were fixed. 17.10.5 fixes both; nothing else changed.

**(1) Possession, not just continuity.** A rotation proof used to be a single
signature by the OUTGOING key over the new bundle. The harbour verified that and
adopted whatever bundle the caller named — so a member could name an **offline**
identity's public bundle as its successor and squat the fingerprint (the
duplicate-fingerprint check only covers identities currently connected). The
squatter could not sign as the victim and gained no authority, but the real
keyholder was locked out of its own fingerprint. The proof now carries a second
signature, by the INCOMING private key, over
`VH-ROTATE-POP-v1 | oldFp | newFp | ts` — bound to the caller's authenticated
fingerprint, so it cannot be lifted onto another rotation.

**(2) Authority is withdrawn by authority.** Any member could file a revocation
against a designated identity and switch that principal off — stickily, because
revocations are keyed to the fingerprint and live in the ledger. A revocation
against a **designated** identity now counts only from an authorised writer: the
harbour root, or a fingerprint named in `VH_AUTHORITIES`. It is refused at
submission (`revocation-requires-authority`) and ignored at consumption, so
records already in a ledger are inert too. **Ordinary identities are unchanged** —
a peer may still withdraw standing, and that is pinned so the rule cannot
over-reach.

**Upgrade impact.** Rotations are produced by the SDK (`client.rotate()`), so
applications that use it need no change; a rotation proof minted by hand from an
older build will be refused — re-issue it with the new key in hand. Revocations
are unaffected unless they target a designated identity, in which case they must
come from an authorised writer. Recovery from an authorised self-revocation is a
config change (`VH_AUTHORITIES`) or a fresh identity: withdrawal is deliberately
sticky.

**What the campaign proves now.** 22/22 attacker-grade attacks refused with the
control intact (was 16/16 + 3 findings): rotation squatting on two sockets, the
fingerprint still free for its real keyholder, a member's revocation of the
operator refused, the operator still delegating afterwards, an authorised
withdrawal honoured. Four **posture** notes remain, stated so a reader can argue
with them — authority-managing is a class, an authorised withdrawal is sticky,
chains only deepen from the root, and designation follows a proven rotation (which
now requires possession).

## 8 · 17.10.4 — RULE 5, and the last self-attestation hole

**The review that produced this release was short: 9.4/10, "RULE 4 is correct but
partial — make Rule 5 about separating capability claims from actual delegable
authority before calling the protocol production-secure."** It was right, and it
came with a reproduction rather than a hypothesis: `heldTokens()` →
`canDelegate()` → `{ ok: true, reason: "attested-granter:holds-action" }`, from
the trust code alone.

**THE FINDING.** RULE 3 asked *may this granter hand out what it HOLDS?* RULE 4
stopped `*`-class tokens from being self-declared. But **holding** was still
established by a **self-signed declaration** for every *named* token. So a
participant could join, `declareCapability(["write:payroll"])` — no `*`, no
forgery, no key compromise, no collusion — and mint a real payroll grant to an
accomplice, and the harbour would record it as `attested-granter:holds-action`.
Closed unbounded self-authority, left the named case standing: the same class of
defect, one size smaller.

**PROTOCOL v0.10.6 — RULE 5: a capability claim is not a licence.** Delegable
authority now has exactly two sources:

- a **live grant** naming the fingerprint as subject (revocation- and
  expiry-aware), or
- a declaration by an **operator-authorized identity** — the harbour root key, or
  a fingerprint named in `VH_AUTHORITIES` (`VH_WILDCARD_AUTHORITIES` is the
  v0.10.5 name and is still read).

Everything else is a claim: descriptive — reputation, capability reporting, audit,
UI — and never a licence. The refusal names the rule: `capability-claim-is-not-authority`.
`*`-class tokens keep RULE 4's `wildcard-authority-not-designated`.

**THE FIVE CASES THE REVIEWER ASKED FOR, ALL PINNED IN THE SUITE:**

| Case | Expected | Result |
|---|---|---|
| self-declared `write:payroll` ⇒ grant | REFUSE | REFUSED (`capability-claim-is-not-authority`) |
| self-declared `admin:finance` ⇒ grant | REFUSE | REFUSED (`capability-claim-is-not-authority`) |
| root-authorized `write:payroll` ⇒ grant | ALLOW | ACCEPTED |
| valid parent ⇒ narrower child | ALLOW | ACCEPTED |
| valid parent ⇒ wider child | REFUSE | REFUSED (`grantor-out-of-scope`) |

**Two consequences that had to be decided, not discovered.**

1. **Designation follows the IDENTITY across a proven key rotation.** Rotation is
   the routine hygiene action; if it silently voided designation, operators would
   simply stop rotating. The harbour records a rotation only after verifying a
   proof signed by the **outgoing** key, and `rotate` is not a member-submittable
   kind (`VOUCH_KINDS`) — so the lineage in the ledger cannot be forged from a
   message. A designated identity's successor inherits the designation,
   transitively. *Grants and revocations stay keyed to the exact fingerprint* —
   deliberately: if grants followed lineage, a revoked key could rotate once and
   walk out of its own revocation. Both halves are pinned by tests.
2. **Upgrade impact is real and stated.** An identity that used to self-declare a
   token and grant it now needs either designation or a grant. The bootstrap for
   a real organisation: name the organisation's key in `VH_AUTHORITIES`, let it
   declare its scope tokens and hand grants to members, who sub-delegate inside
   them. A fresh harbour with no designation hands out nothing it was not told to.
   `VH_GRANT_POLICY=compat` restores the old semantics for migration only.

**THE CAMPAIGN WAS REWRITTEN, AND FOUND ONE MORE THING.** RULE 5 changed what
"legitimate" means, so `protocol/wcarena/adversarial-campaign.mjs` no longer lets
any actor declare its own authority: the harness now starts its own real harbour
with an operator-designated identity, plays that operator, and puts **every
honest actor on GRANTED authority** — so a refusal proves the *bound*, not the
absence of a setup. It grew from 11 to **14 attack classes**, the two new ones
being exactly the reviewer's named cases, and it now reports **14/14 refused with
the legitimate control intact**, every refusal for its own reason (`grantor-out-of-scope`,
`capability-claim-is-not-authority`, `wildcard-authority-not-designated`,
`no-authorization`) — where the first rewrite attempt had several attacks
"passing" for the wrong reason (`grantor-unattested`). Running it surfaced a
second-order defect worth naming: an identity the **operator had designated** was
still refused as `grantor-unattested`, because RULE 1 asked for a self-declared
capability or an endorsement and designation was not in that list. Authority the
operator believes it delegated, that the protocol will not let it use — a trap.
Fixed at the root: **designation is attestation**, since the operator's own
statement about who an identity is outweighs a claim the harbour merely records.
Pinned in the suite.

**The other shipped harnesses were re-based too.** `wcarena/v104-authority-matrix.mjs`
(**10/10** — same both-directions proof, now on granted authority) and
`wcarena/governance-attacks.mjs` (control permitted, 4/4 refused) went through a
shared `wcarena/_harbor.mjs`; attaching to somebody else's harbour no longer works
for them, because designation is a boot-time decision and without an operator the
legitimate half of a matrix would be unprovable. `wcarena/exploit-self-attestation.mjs`
is attacker-only and still passes unchanged (every leg refused).

**Gate.** `protocol/test/selftest.js` **152/152** (was 140) — twelve new checks,
including the named-claim refusals, the "same token GIVEN is delegable" positive
path, the lineage clause (proven rotation carries designation; an unrecorded
successor carries nothing; a rotation carries no GRANTS), and the pin that
lineage records are never member-submittable. Nothing else in the protocol was
touched: no new subsystem, no new wire type, no loosened gate.

its own definition, plus two comments in `harborTeams.ts`. Every other reference
was a probe. A passing end-to-end harness proves the architecture works **when a
test wires it**; it says nothing about whether the shipped application exposes it.

### What the mount is

One bootstrap, in the order the product claims it runs
(`src/mission/a2aRuntime.ts` → `startA2ARuntime()`):

```text
load harbor identity   ECDSA P-256 keypair + sha256 fingerprint
load the team          the teammates this harbor will route work to
sign the A2A card      JWS over the canonical card bytes (strict v1.0.0 shape)
attach the handler     GuardRail scan → routing → this harbor's human gate
attach the risk policy the receiver re-classifies; a sender cannot downgrade
attach the LiveBridge  real TeamExecutor · real CLI · real git · repo's own test
listen                 GET /.well-known/agent-card.json · POST / (JSON-RPC 2.0)
```

`tools/vh-host.entry.ts` is the process around it; `npm run host:build` bundles
it to `tools/vh-host-engine.mjs` and byte-pins it (`.sha256`) exactly the way the
MCP engine is pinned; `npm run host` verifies that pin before it will listen.

Two supporting pieces had to exist for the mount to be honest:

- **`nodeRunnerDeps()`** — the host-side `TeamRunnerDeps`. The app's
  `hostRunnerDeps` rides the Tauri IPC layer on desktop and *simulates* in the
  browser; a mounted harbor needs real `spawn`, real git, real fs and the
  repository's own test command as the verdict.
- **A bind port on the transport.** `createA2AServer()` always listened on an
  ephemeral port, while the card it serves is *signed for* an interface URL. A
  mount that bound 33951 and advertised 3457 would be serving a card that lies
  about its own interface. `A2AServerOptions.port` closes that, and the runtime
  throws if the bound port is not the advertised one.

### The receiver grades the request itself

`DelegationPacketV10.tier` is written by the **sending** harbor, and the receiver
believed it — so a remote harbor could label a `git push --force` as `"safe"` and
walk past the receiver's human gate. That contradicts §10 of this codebase in so
many words ("the classification is derived from the action itself — not asserted
by the agent that wants to perform it"). `receiverRiskVerdict()` now runs the
inbound task through the receiver's own risk table and takes the **worse** of the
two. It can only upgrade. Every settled record carries the verdict as
`receiverPolicy`, so a sender can see when its label was overruled and why.

### The gate

`probe/a2aRuntime.test.ts` — **48 checks**, and the headline is §3: two
independently running VH processes. The receiver mounts and publishes its JWK; a
stranger discovers the card over HTTP and verifies the signature; the sender
process delegates; the receiver process runs a real TeamExecutor mission (2
seats, `cross-vendor` gate PASS, real worktree, the repo's own test as the
verdict) and returns a sealed `vh-proof-receipt/2` that verifies in the sender's
process **and in a third process** via `tools/verify-receipt.mjs` (exit 0 with
the issuer key pinned out of band; exit 3 — integrity valid, issuer UNVERIFIED —
without it, which is the verifier refusing to overclaim). The rest pins: a
doctored engine fails closed instead of listening; a mounted harbor that cannot
execute refuses in words; a repository whose tests fail comes back
`executed-failed`; and the risk-policy ladder, including that a sender declaring
`"risky"` is never talked down.

### What is still not wired

`npm run host` does not spawn `protocol/src/server/harbor.js` alongside the
listener, and the receiver gate does not yet consult that harbour's grant ledger.
Authority on this door is: JWS-verified card identity + bearer token + the
receiver's own risk policy + its human gate. Consulting the Warrant harbour's
grant check from the receiver gate is the next seam — the two processes are the
two halves of "authorize", and today only the A2A half is in the same boot.

# Vouch Harbor 18.1.0 "TeamEvolve" — upgrade notes

Base: 18.0.1 "Generalist" (the VH-19 front door, wired and probe-pinned).
18.1.0 ships the feature both external reviews named as THE differentiator
still missing — and two supporting upgrades. Protocol unchanged at v0.10.7.

## 1 · Cross-user Team-Evolve — the team itself learns

The vision: Member A-VH ↔ Qwen-VH share a team; the team, as a unit, gets
better from working together; once proven, the evolved configuration is
reusable. `src/vh19/teamEvolve.ts` implements exactly that loop, honestly:

- **The joint-run ledger.** Every peer-delegated run through
  `askVH19({ team })` is recorded with its REAL outcome
  (`verified` / `failed` / `refused`), the specialists that ran, and the
  receipt digest when one was actually sealed (host runtime). Teams are
  identified order- and case-independently.
- **Proposals come from the record, never from imagination.** Minimum bar:
  ≥3 runs, ≥1 verified, ≥2 distinct specialists proven in verified runs.
  Below the bar, the refusal says what is missing. A proposal carries its
  recommended composition, rationale citing the real success rate, its
  source-run ids, and a computed digest.
- **User 2's consent is structural.** `approveTeamEvolution` refuses partial
  approvals (naming who is missing), duplicate approvals (one voice per
  member), outsider approvals, and any decline. There is no code path that
  adopts a configuration on one signature. The door collects the local
  member's approval and states plainly that peer approvals arrive via the
  A2A host runtime — the UI cannot forge a peer's voice, and the probe pins
  that it cannot.
- **The evolved config leans, visibly.** Recommended specialists get a
  labeled +2 (`team-evolved preference (config vN)`) in routing decisions;
  the lean never injects a specialist absent from the decision. Configs are
  versioned, digest-stamped artifacts naming their approvals and source runs.
  Revocation is one click.

## 2 · Category-scoped autonomy

The 90% exam can be scoped to one category (the door has the selector).
A pass grants autonomy for THAT category only; the gate consults the scoped
grant via `autonomyCovers`; the overall grant still covers everything;
category revocation leaves other scopes untouched. The override floor is
unchanged — permanent, unstoreable-off, one-click.
